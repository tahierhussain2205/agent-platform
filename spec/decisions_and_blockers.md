# Decisions and Blockers

Running log kept while implementing `implementation_plan.md`. Every decision made without asking is recorded here with its reason, and every blocker with the workaround in place and what is needed to resolve it properly.

- **Decisions** are numbered `D-NNN` and grouped by phase.
- **Blockers** are numbered `B-NNN`. Each lists: what is blocked, the workaround in use, and what is needed to resolve it.

## Phase 3: Database and migrations

| # | Decision | Reason |
|---|---|---|
| D-032 | Working assumption about Render Postgres: the default user owns the database and has CREATEROLE but is not a superuser and has no BYPASSRLS (B-010). | Render docs say users created with `CREATE USER` are "not managed by Render", implying CREATEROLE; nothing suggests superuser. In PostgreSQL 16 only superusers (or BYPASSRLS holders) can grant BYPASSRLS. |
| D-033 | Migration 001 gets one more documented change: the four role attribute statements run in a block that skips `insufficient_privilege` with a notice, then fails closed if `app_user` or `app_vault` can bypass RLS; a non superuser migrator grants itself SET on `app_owner`. The drift test reconstructs `spec/schema.sql` exactly from 001 to pin the change. | Lets the tested schema run unchanged on managed Postgres, without weakening isolation. |
| D-034 | The application never relies on BYPASSRLS: identity sync and maintenance use security definer functions owned by `app_owner` (the spec's fallback, used everywhere for one code path). | Works on Render whatever the default user can do; also least privilege (execute on a function instead of table wide bypass). |
| D-035 | Locally, Compose creates a non superuser `agent_admin` (CREATEROLE, owns `agent`) through a Postgres init script as a stand-in for Render's provisioning; migrations run as it. Tests run migrations as superuser and as a Render-like user. | Local should fail the same way Render would. |
| D-036 | One login user per component (`api_service`, `worker_service`, `vault_service`, `identity_service`, `maintenance_service`), each a member of exactly one NOLOGIN role, created or updated by `app migrate` when its `DB_<COMPONENT>_PASSWORD` is set. Attributes and memberships are verified after every change (fail closed). | Plan phase 3; invariant 2. Verification catches drift such as an extra role granted by hand. |
| D-037 | Passwords are sent to Postgres as SCRAM-SHA-256 verifiers computed client side; minimum length 16. | The plaintext never reaches the server or its statement log. |
| D-038 | Components connect with `DATABASE_URL` (PgBouncer pool) with the credentials swapped for their own (`Settings.component_dsn`). On Render, passwords come from one generated env group per component; each service references only what it needs, except `api-staging`, which holds all of them because its `preDeployCommand` creates the users. Only `api-staging` holds the migration URL. | Least privilege within Render's model. Known trade-off: the API process environment holds credentials it only uses in `app migrate`; a dedicated migration job would remove that later. |
| D-039 | `app maintenance` runs isolated jobs as `maintenance_service` (phase 3: partitions, 3 months ahead) and exits 1 if any job failed. | One failing job must not hide the others; the cron's exit status shows failures on Render. |
| D-040 | The schema test suite builds a `world` with a row in every tenant table and checks isolation generically for all 31 tenant tables, plus the 13.4 guarantees (295 tests); a meta test forces new tenant tables into the suite; `scripts/schema_mutations.sh` weakens 10 guarantees one at a time and requires the suite to fail on each (also in CI). | The spec's "28 tests" were not provided as code, so they were rewritten from section 13.4, more thoroughly. Mutation checks prove the tests can fail. |
| D-041 | Long lines (E501) are allowed in tests. | SQL statements in tests read better on one line; application code keeps the 110 limit. |
| D-042 | Migrations forward Postgres notices to the log. | Operators see "skipped, needs a superuser" in the deploy log on managed Postgres. |

## Phase 4: Backend core

| # | Decision | Reason |
|---|---|---|
| D-043 | The unit of work is a pure ASGI middleware that wraps `send` and commits when the response start message passes through (status below 400), replacing the response with the mapped error if the commit fails. Handlers bind the org lazily (`await uow.bind(org_id)`). | Meets "commit before the response starts" regardless of FastAPI's dependency teardown timing, and handles deferred constraints that only fail at commit. Requests that never touch tenant data take no connection. |
| D-044 | Unhandled exceptions are turned into the JSON 500 inside the request context middleware (after the unit of work rolled back), not by Starlette's outermost handler. | The 500 still carries the request id header and never leaks exception text. |
| D-045 | Database error bodies carry a generic message per class plus the constraint name; raw database messages are only logged. | Raw messages can contain row values. |
| D-046 | JSON logging with the standard library (custom formatter, contextvars) instead of a logging library; a regex redaction filter is applied to every message, extra field and traceback as a backstop. Health and readiness checks log at debug. | One small dependency free module; redaction catches mistakes, it does not replace "never log secrets". |
| D-047 | OpenTelemetry with OTLP over HTTP; tenant id stamped on spans by a span processor once the unit of work binds; query strings stripped from server spans; psycopg spans with statement text only (no SQL commenter). | Spec 11.4 (tenant id on every span, redaction before storage). OAuth callbacks carry codes in query strings. |
| D-048 | Local PgBouncer uses a wildcard database and `auth_query`, so every login user (including test users) authenticates against Postgres without editing a user list. The API and worker connect through it; migrations do not. | Mirrors a managed pooler and lets the middleware tests run through real transaction pooling, as the plan requires. |
| D-049 | Envelope encryption: AES-256-GCM data keys per secret, wrapped with a per tenant key derived by HKDF from a versioned master key (`ENCRYPTION_KEYS`, `ENCRYPTION_ACTIVE_KEY`); associated data binds each ciphertext to its org and a `<table>:<row id>` context; `kms_key_id` records `local:<version>`; `rewrap()` supports rotation. A cloud KMS provider can implement the same `KeyProvider` interface. | Plan phase 4 (master key from a Render secret, key versions recorded). Binding prevents a ciphertext being copied to another row or tenant. |
| D-050 | Object storage target: Cloudflare R2 (S3 API, region `auto`) for staging and production, behind a generic S3 client; keys under `tenants/<org_id>/`, references checked against the caller's org. | Open item "S3 or R2" (needed by phase 4). R2 is cloud neutral and has no egress fees; switching to S3 is configuration only. No account yet (B-011). |
| D-051 | `/readyz` checks Postgres (as `api_service`) and Key Value with 2 second timeouts and never includes connection details; Render's health check stays on `/healthz`. | Plan rule 9; a dependency outage should not make Render restart healthy processes. |

## Phase 5: Identity and admin console

| # | Decision | Reason |
|---|---|---|
| D-052 | A `fakes` service (own package and image, Compose and tests only) hosts SaaS stand-ins; Clerk is the first. It mirrors Clerk's Backend API shapes, v2 session token claims, JWKS and Svix signed webhooks, and adds a small dev sign in API in place of ClerkJS. State persists to a volume; `/_admin/reset` restores the seed but keeps the signing key. | Blocker B-003. Faking at the HTTP boundary exercises our real verification, webhook and Backend API code; keeping the key avoids invalidating cached JWKS when tests reset data. |
| D-053 | The console has one `AuthAdapter` interface with two implementations: `@clerk/react` (Core 3, lazy loaded) when `VITE_CLERK_PUBLISHABLE_KEY` is set, and a dev adapter for the stand-in otherwise. | Same app code either way; the dev bundle never loads Clerk. |
| D-054 | Token verification follows spec 14.3 and Clerk's manual verification guide: RS256 only, JWKS by `kid` with a rate limited refresh (10 s), issuer check, 5 s leeway, `azp` required and allow listed, pending sessions refused, org from `o.id` with `org_id` fallback. Privilege comes from `app.resolve_console_identity`, never the token. | Spec 14.3. Requiring `azp` (Clerk says "skip if absent") is stricter: console tokens always carry it. |
| D-055 | Identity sync and maintenance style writes use security definer functions (migration 002); request code never writes `org_memberships`. | Plan phase 5 ("the console never writes memberships directly") and D-034. |
| D-056 | Console identity changes are mirrored synchronously: apply the change through the identity function in an `identity_service` transaction (the last admin guard can refuse it there), call Clerk inside that transaction, commit only if Clerk succeeded. The webhook that follows is idempotent. | Clerk stays the source of truth while the database guard stays authoritative; no window where Clerk and the database disagree on a refused change. |
| D-057 | Webhooks are deduplicated by `svix-id` in Key Value with a "processing" marker (60 s, a concurrent retry gets 409 so Svix retries later) and a "done" marker (24 h); failures release the claim and return 500. Unknown event types are acknowledged. | Svix retries; at-least-once delivery must not apply an event twice, and a failed attempt must stay retryable. |
| D-058 | Each membership stores `identity_event_at`; identity functions take the event time (Clerk's payload `timestamp`, or the transaction time for console mirroring), ignore older events and always advance the stamp, even when an event confirms the current state. Migration 002 was amended in place for this (it only existed in this unmerged phase and local databases). | Found by the e2e suite: a late `organizationInvitation.created` resurrected a revoked invitation. Small clock skew between Clerk and the database is accepted; a reconciliation job can repair rare drift. |
| D-059 | When Clerk deletes a user who is an org's last active admin, that membership is kept (and audited) instead of failing the webhook forever. | The database never leaves an org without an admin; an operator is alerted through the audit log to appoint one. |
| D-060 | Removing a member in the console also removes them in Clerk, so they end up in no org and Clerk sends them to create or choose one; a stale token for the old org is refused by the API (`not_a_member`). | Matches Clerk's "organization required" behavior. |
| D-061 | Console API errors share one JSON shape (`code`, `message`, `request_id`, optional `fields`) for auth, validation, HTTP and database errors; the UI shows the request id with every error. | Supportable errors; the request id links the UI to logs and traces. |
| D-062 | Console email validation is a permissive pattern instead of `pydantic.EmailStr`. | `email-validator` rejects reserved domains such as `.test`, which internal and test domains use; Clerk delivers the email anyway. |
| D-063 | Right after signup or accepting an invitation the console retries `/api/me` answers `not_a_member` / `membership_pending` for about 8 seconds before showing "No access". | Clerk webhooks reach the API asynchronously; the same lag exists with real Clerk. |
| D-064 | Console stack: React Router (v8), TanStack Query (query keys include the active org, so switching orgs refetches), Tailwind CSS v4, native `<dialog>` modals. | Small, standard, accessible building blocks; no component library dependency. |
| D-065 | The public Clerk webhook endpoint refuses bodies over 1 MiB (declared or actual) before verifying signatures. | Cheap protection against oversized payloads on an unauthenticated endpoint; real Clerk events are a few KB. |

## Phase 6: Slack app and ingress

| # | Decision | Reason |
|---|---|---|
| D-066 | The `fakes` service gains a Slack stand-in: Web API methods we call (`oauth.v2.access`, `auth.test`/`revoke`, `conversations.*`, `chat.*`, `users.info`/`lookupByEmail`, `views.publish`) with Slack's envelope and error codes, per method 429s on demand, an OAuth v2 authorize page, signed event and interaction deliveries with `X-Slack-Retry-Num` retries, and a vanilla JS Slack-like UI. Seeded from the shared fixture plus sample channel history for later phases. | Blocker B-004. Faking at the HTTP boundary keeps our real signature, OAuth, pagination, retry and rate limit code under test; the UI lets Playwright test the user's side of Slack. |
| D-067 | Workflow inputs from Slack carry references only (team, channel, channel type, user, ts, thread ts, event id), never message text. | Invariant 7: raw Slack messages are not stored, and Temporal history is storage. The agent reads the text through the API when it needs it (phase 7). |
| D-068 | Two dedupe layers: a Key Value claim on the event id (released, with a 500, if the workflow cannot be started, so Slack's retry can succeed), and a Temporal workflow id `slack-{event_id}` (an "already started" error counts as success). | Slack delivers at least once and retries slow acknowledgements; neither layer alone covers both a Key Value outage and a crash between claim and start. |
| D-069 | Events for unknown or uninstalled workspaces, bot messages and unsupported event types are acknowledged with 200 and logged. | A non 2xx makes Slack retry and eventually disable the app's event subscription. |
| D-070 | OAuth `state` is HMAC signed (`SLACK_STATE_SECRET`) with org, membership, nonce and issue time; valid 10 minutes; the nonce is single use in Key Value; the installer must still be an active admin when the callback arrives. Failures redirect to the console with an error code the Slack page explains. | CSRF and replay protection without server side sessions; the console shows a useful message instead of a raw error page. |
| D-071 | Install commits the workspace, the `slack` integration enablement, the org connection and the audit row first, then stores the encrypted bot token through the vault. If storing fails, the install is undone (workspace uninstalled, connection revoked) and the token is revoked at Slack. | The vault uses its own `vault_service` connection, which cannot see uncommitted rows (the secret has a foreign key to the connection). Undoing keeps the console from showing a connection without a token. |
| D-072 | One workspace per org, one org per workspace: installing a second workspace into an org (`other_workspace`) or a workspace connected to another org (`workspace_taken`) is refused. Reinstalling the same workspace replaces the connection. | Spec data model (`workspaces` unique per active external id); keeps tenant boundaries simple. |
| D-073 | Slack errors that retrying cannot fix (`channel_not_found`, `not_in_channel`, `invalid_auth`, `token_revoked`, `missing_scope`, `invalid_blocks`, ...) become non retryable `ApplicationError`s. Private notices try `chat.postEphemeral`, fall back to a DM, and are dropped if both fail permanently. | Temporal would otherwise retry for hours; a private notice must never fail the whole request. |
| D-074 | The outbound rate limiter uses fixed one second windows per workspace and method bucket in Key Value (`chat.*` 5/s, `views.*` 3/s, Tier 3 1/s, Tier 4 2/s), waiting up to 30 s for a slot; the client also retries 429s after `Retry-After` and 5xx with backoff. | Shared across API and worker processes; an atomic `INCR` with expiry is simple and good enough. Bursts at window edges stay well below Slack's per minute allowances. |
| D-075 | Progress updates to the same message are coalesced: each send takes a version number in Key Value, and an update still waiting for a rate limit slot is dropped if a newer one arrived. | Spec 14.4 ("progress updates are coalesced"); stale progress is useless and wastes the `chat.update` budget. |
| D-076 | Until phase 7's `external_actions`, the thread acknowledgement is made idempotent with a Key Value marker per event id. | Activities run at least once; a retried activity must not post twice. |
| D-077 | Requesters are identified by platform identity, else by matching the Slack profile email to an active or invited member (the identity is then recorded). A membership already linked to another Slack user in the workspace is refused. Deleted users and bots are never members. | Spec 4.1.2 (invited users work before console signup) and P2; refusing a second link stops an email reused by another Slack account from inheriting access. |
| D-078 | Access requests: one pending request per Slack user and workspace (unique index); only a new request DMs the active admins (with Invite and Dismiss); repeat mentions only get the private notice. Invite from Slack or the console uses the same invite path as the Members page (Clerk invitation plus identity mirroring), then updates the DM in place. | Spec 4.1.7 and P3 without spamming admins. One invite path keeps Clerk the source of truth. |
| D-079 | Channel sync stores all channels the bot can see, member lists only for allowlisted channels the bot is in, and archives (never deletes) channels that disappeared. Allowlisting a channel the bot is in syncs its members immediately; removing it from the allowlist pauses schedules delivering there (database trigger) and the console reports how many. | Member lists matter only where the agent can read; archived rows keep schedules and audit references intact. |
